## Мотивация

Яндекс Метрика показывает действия посетителей онлайн-магазина, но не охватывает партнёрский API и внутреннее прохождение заказа через CRM, RabbitMQ и MES. Сейчас компания узнаёт о задержках из обращений клиентов и не может определить, на каком этапе возникла проблема.

Мониторинг должен позволить:

- Обнаруживать зависшие заказы до обращения клиента;
- Определять, где возникла задержка: в API, RabbitMQ, приложении или базе данных;
- Видеть влияние партнёрской нагрузки на MES и работу операторов;
- Находить причины медленной загрузки дашборда MES;
- Оценивать запас вычислительных ресурсов и планировать масштабирование;
- Контролировать результат изменений после их выпуска.

Для бизнеса это означает сокращение количества просроченных заказов, снижение риска потери контрактов и сокращение времени поиска и устранения сбоев.

## Выбор подхода к мониторингу

### RED

Метод RED применяется к Shop API, CRM API и MES API:

- Rate — количество запросов в секунду;
- Errors — количество и доля ошибочных ответов;
- Duration — продолжительность обработки запросов.

Эти показатели позволяют увидеть рост нагрузки, ошибки и увеличение времени ответа с точки зрения клиентов и операторов. Для MES API отдельно контролируются запросы расчёта стоимости и получения списка заказов.

### USE

Метод USE применяется к экземплярам приложений и баз данных:

- Utilization — использование CPU, памяти, диска и подключений к базе данных;
- Saturation — очередь ожидающих запросов, исчерпание пула подключений и накопление сообщений RabbitMQ;
- Errors — ошибки экземпляров, баз данных и инфраструктурных компонентов.

Метод помогает отличить нехватку ресурсов от ошибки в приложении или неэффективного SQL-запроса.

## Метрики

**Правила формирования ярлыков**

Для всех технических метрик используются общие ярлыки `environment`, `service` и `instance`. Идентификаторы пользователей, заказов и файлов не используются как ярлыки метрик.

В ярлык `route` записывается шаблон маршрута без идентификаторов заказов и других уникальных значений. Для MES API отдельно контролируются расчёт стоимости и получение списка заказов. Ярлык `source` разделяет запросы онлайн-магазина, партнёров и внутренних пользователей.

В ярлыке `operation` указывается короткое постоянное имя операции, например `mes_orders_dashboard`, без текста SQL-запроса и его параметров. Длительность таких операций измеряет API, который выполняет запрос к базе данных.

**Прохождение заказов**

RED и USE не показывают, дошёл ли конкретный заказ до следующего бизнес-статуса. Поэтому дополнительно собираются метрики количества заказов, длительности нахождения в статусах и ошибок перехода. Эти метрики позволяют обнаруживать заказы, которые слишком долго остаются в одном статусе или не переходят на следующий этап.

| Метрика | Компоненты | Назначение | Дополнительные ярлыки |
| --- | --- | --- | --- |
| `partner_order_requests_total` | MES API | Показывает количество партнёрских запросов на создание заказа, принятых MES API | `result` |
| `orders_created_total` | Shop API, CRM API | Показывает количество фактически созданных заказов и позволяет сравнить поток B2C- и партнёрских заказов | `source` (`shop`, `partner`), `result` |
| `order_status_transitions_total` | Shop API, CRM API, MES API | Показывает количество успешных и ошибочных переходов между статусами | `from_status`, `to_status`, `source`, `result` |
| `orders_in_status` | API — владелец статуса | Показывает количество заказов в каждом статусе и помогает заметить их накопление на одном этапе | `status`, `source` |
| `oldest_order_in_status_seconds` | API — владелец статуса | Показывает возраст самого старого заказа в статусе и позволяет обнаружить зависший заказ | `status`, `source` |
| `price_calculation_duration_seconds` | MES API | Показывает распределение времени расчёта стоимости | `source`, `result` |

Для `orders_in_status` и `oldest_order_in_status_seconds` назначается единственный владелец каждого статуса:

| Владелец | Статусы |
| --- | --- |
| Shop API | `INITIATED`, `FILE_UPLOADED`, `SUBMITTED` |
| MES API | `PRICE_CALCULATED`, `MANUFACTURING_STARTED`, `MANUFACTURING_COMPLETED`, `PACKAGING`, `SHIPPED` |
| CRM API | `MANUFACTURING_APPROVED`, `CLOSED` |

Каждый API рассчитывает значения `orders_in_status` и `oldest_order_in_status_seconds` по данным своей базы только для закреплённых за ним статусов. Если API запущен в нескольких экземплярах и каждый экземпляр видит одну базу, в PromQL используется `max by (environment, status, source)`, а не сумма значений по `instance`.

Расхождения статусов между Shop DB и MES DB проверяются отдельной периодической сверкой по `order_id`. Текущее количество расхождений записывается в gauge `order_state_mismatches`, а идентификаторы заказов — в логи для расследования.

**Shop API, CRM API и MES API**

| Метрика | Назначение | Дополнительные ярлыки |
| --- | --- | --- |
| `http_requests_total` | Считает запросы и используется для расчёта RPS и доли ошибок. Заменяет отдельные счётчики HTTP 200 и HTTP 500 | `method`, `route`, `status_code`, `source` |
| `http_request_duration_seconds` | Показывает распределение времени ответа и позволяет вычислять p50, p95 и p99 | `method`, `route`, `status_code`, `source` |
| `http_requests_in_progress` | Показывает количество одновременно обрабатываемых запросов и насыщение приложения | `route`, `source` |

**RabbitMQ**

| Метрика | Назначение | Дополнительные ярлыки |
| --- | --- | --- |
| `rabbitmq_detailed_queue_messages_ready` | Показывает количество сообщений, которые находятся в очереди и готовы к передаче обработчикам. Рост значения означает, что обработчики не успевают разбирать очередь | `queue`, `vhost` |
| `rabbitmq_detailed_queue_messages_unacked` | Показывает сообщения, переданные обработчикам, но ещё не подтверждённые. Позволяет обнаружить зависшие обработчики | `queue`, `vhost` |
| `rabbitmq_detailed_queue_messages_ready` для DLQ | Показывает количество сообщений в очереди, привязанной к Dead Letter Exchange | `queue`, `vhost` |

**Приложения и базы данных**

| Метрика | Компоненты | Назначение | Дополнительные ярлыки |
| --- | --- | --- | --- |
| `process_cpu_utilization` | Shop API, CRM API, MES API | Показывает загрузку процессора и помогает проверить гипотезу о перегрузке приложения | `service`, `instance` |
| `process_memory_utilization` | Shop API, CRM API, MES API | Показывает использование памяти и позволяет обнаружить её исчерпание или утечку | `service`, `instance` |
| `db_cpu_utilization` | Shop DB, MES DB | Показывает вычислительную нагрузку базы данных | `database`, `instance` |
| `db_memory_utilization` | Shop DB, MES DB | Показывает использование памяти базы данных | `database`, `instance` |
| `db_connections` | Shop DB, MES DB | Показывает количество подключений и приближение к пределу пула или СУБД | `database`, `state` |
| `db_query_duration_seconds` | Shop API, MES API | Измеряется в API вокруг вызова базы данных и позволяет обнаружить медленные именованные операции, включая запрос дашборда MES | `database`, `operation` |
| `db_storage_utilization` | Shop DB, MES DB | Показывает занятое место и запас до исчерпания диска | `database`, `instance` |

### Показатели насыщенности

Раздел относится к дополнительной части задания. До запуска мониторинга у команды нет данных о нормальной нагрузке, поэтому пороги задаются как начальные. После накопления статистики за две недели их необходимо скорректировать.

| Показатель | Начальный порог | Обоснование | Реакция |
| --- | --- | --- | --- |
| Сообщения в Dead Letter Queue | В очереди находится хотя бы одно сообщение | В Dead Letter Queue попадают заказы, которые не удалось обработать штатно | Создать инцидент и не закрывать его до разбора всех сообщений в очереди |
| Возраст заказа в статусе | Превышен допустимый срок для конкретного статуса | Допустимое время различается для расчёта стоимости, производства, упаковки и доставки | Создать обращение поддержке с указанием статуса и системы-владельца |
| Доля HTTP 5xx | Более 5% в течение 5 минут | Устойчивый рост серверных ошибок означает сбой приложения или его зависимости | Оповестить дежурного инженера и проверить состояние приложения и последнюю поставку |
| Время ответа MES API | p95 более 2 секунд в течение 10 минут, кроме расчёта стоимости | Интерактивные операции операторов не должны ждать длительный расчёт стоимости | Проверить MES API, базу данных и SQL-запрос дашборда |
| Одновременно обрабатываемые HTTP-запросы | Более 80% от настроенного лимита в течение 10 минут | Приближение к лимиту означает, что новые запросы скоро начнут ожидать освобождения ресурсов | Проверить длительные запросы и зависимости; при устойчивом росте нагрузки увеличить число экземпляров |
| Накопление сообщений в основной очереди RabbitMQ | Количество готовых к обработке сообщений непрерывно растёт в течение 10 минут | Устойчивый рост очереди означает, что потребители не успевают обрабатывать входящий поток | Проверить доступность и скорость потребителей; при нехватке производительности увеличить число потребителей |
| CPU приложения | Более 80% в течение 15 минут | Длительная высокая загрузка оставляет мало ресурсов для роста нагрузки | Создать предупреждение и проверить необходимость увеличения ресурсов или числа экземпляров |
| Память приложения или базы данных | Более 85% в течение 15 минут | Дальнейший рост может привести к завершению процессов или активному использованию swap | Проверить потребление памяти и при необходимости увеличить ресурсы |
| Подключения к базе данных | Более 80% от установленного предела в течение 10 минут | Исчерпание подключений не позволит приложениям выполнять новые запросы | Проверить пулы подключений и длительные SQL-запросы |
| Заполнение диска базы данных | Более 80% | Оставшегося места должно хватать на рост данных и проведение служебных операций | Создать предупреждение и запланировать увеличение хранилища; при достижении 90% создать критический инцидент |

## План действий

1. Согласовать названия метрик, набор ярлыков, допустимые сроки нахождения заказа в каждом статусе и ответственных за реакцию;
2. Добавить в Shop API, CRM API и MES API эндпоинты `/metrics` и сбор RED-метрик;
3. Добавить бизнес-метрики создания заказа, переходов статуса, возраста заказа и длительности расчёта стоимости с назначением владельца каждого статуса;
4. Включить плагин `rabbitmq_prometheus` и проверить метрики очередей, неподтверждённых сообщений и очереди, привязанной к Dead Letter Exchange;
5. Добавить в Shop API и MES API измерение длительности выбранных SQL-операций и подключить инфраструктурные метрики экземпляров приложений и Managed PostgreSQL, включая CPU, память, подключения и хранилище;
6. Развернуть Prometheus для сбора и хранения временных рядов;
7. Подключить Prometheus к Grafana и создать дашборды «Заказы», «API», «RabbitMQ» и «Инфраструктура»;
8. Настроить в Grafana правила оповещения и отправку уведомлений ответственным сотрудникам;
9. Проверить мониторинг в release-окружении с помощью тестовых ошибок, задержек и накопления сообщений;
10. Включить сбор метрик в prod, накопить базовый профиль за две недели и скорректировать пороги;
11. Зафиксировать инструкцию для поддержки: как проверить сработавшее предупреждение, найти связанный компонент и передать инцидент разработчикам.
