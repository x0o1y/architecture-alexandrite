## Анализ

Кешировать имеет смысл серверную выдачу списка заказов для дашборда MES. Первая страница кешируется при первом открытии дашборда, остальные — по мере обращения к ним. В кеше хранится только представление списка, необходимое дашборду. Карточки заказов, результаты расчёта стоимости и операции записи не кешируются.

Решение основано на предположении, что операторы обновляют дашборд чаще, чем заказы создаются или меняют статус. Это следует из условия: операторы конкурируют за новые заказы и повторно открывают первую страницу, чтобы быстрее взять появившийся заказ в работу. Между изменениями списка повторные запросы возвращают одинаковые данные и могут обслуживаться из кеша. Предположение проверяется по частоте переходов статуса, запросов дашборда и hit rate кеша.

## Мотивация

Операторы MES долго ждут загрузки списка заказов. Фильтрация и пагинация не устранили проблему, а повторные запросы страниц снова обращаются к MES DB. Чаще всего операторам нужна первая страница с самыми новыми заказами выбранного статуса.

Серверное кеширование страниц списка заказов позволит:

- Сократить время загрузки дашборда MES;
- Уменьшить количество повторяющихся запросов к MES DB;
- Снизить конкуренцию операций чтения с изменением статусов и другими запросами MES;
- Сохранить работоспособность чтения при недоступности кеша за счёт обращения к MES DB.

## Предлагаемое решение

**Тип кеширования и компоненты**

Для дашборда применяется серверное кеширование. Общий Redis размещается между MES API и MES DB. MES API управляет чтением, заполнением и инвалидацией кеша.

Клиентское HTTP-кеширование не выбрано: у каждого оператора появился бы собственный кеш, а изменение статуса заказа у одного оператора не обновило бы данные у остальных. Общий серверный кеш снижает нагрузку на MES DB для всех операторов и позволяет централизованно инвалидировать устаревшие данные.

Для каждого статуса MES DB хранит счётчик поколения кеша в таблице `status_cache_generation`. Начальное значение счётчика — `1`, при каждом изменении списка оно увеличивается на единицу. Например, если для статуса `SUBMITTED` текущее поколение равно `7`, ключ первой страницы имеет вид `mes:orders:SUBMITTED:v7:page:1:size:20`. После изменения списка поколение увеличивается до `8`, и MES API обращается уже к ключам с `v8`. Redis хранит только страницы заказов. Страницы с `v7` больше не читаются и позднее удаляются по TTL. Значение страницы содержит список заказов, отсортированных от новых к старым.

### Cache-Aside

Для чтения используется Cache-Aside:

1. MES API получает из MES DB текущее поколение выбранного статуса;
2. MES API формирует ключ страницы с этой версией и ищет список заказов в Redis;
3. Если ключ найден, MES API возвращает сохранённый список;
4. Если ключ не найден, MES API запрашивает список в MES DB;
5. Полученный список записывается в Redis с TTL и возвращается оператору.

MES DB остаётся источником актуальных данных. Если Redis недоступен при чтении или записи страницы, MES API записывает `WARN` и увеличивает счётчик `redis_cache_errors_total` с ярлыком `operation=read` или `operation=write`. Список запрашивается из MES DB и возвращается оператору без кеширования.

Cache-Aside выбран потому, что он ускоряет повторное чтение дашборда, позволяет хранить готовое представление списка и не делает запись заказа зависимой от Redis.

Write-Through не выбран: изменение статуса пришлось бы синхронно записывать в MES DB и перестраивать несколько списков в кеше. Это усложнило бы операцию записи и сделало её зависимой от Redis. Refresh-Ahead не используется как единственный паттерн, потому что фоновое обновление всех страниц создавало бы запросы к MES DB независимо от обращений операторов.

### Cache-Aside и Refresh-Ahead

Второй вариант сохраняет Cache-Aside для всех страниц и дополнительно применяет Refresh-Ahead к первым страницам часто просматриваемых статусов. Фоновая задача MES API обновляет эти страницы незадолго до истечения TTL. Остальные страницы кешируются только после обращения оператора.

Такой вариант уменьшает количество кеш-промахов на первой странице после истечения TTL. При отсутствии значения в Redis MES API по-прежнему получает страницу из MES DB по правилам Cache-Aside.

**Выбор решения**

**Для внедрения выбран Cache-Aside.** Он не создаёт фоновых запросов к MES DB и требует меньше доработок MES API. Комбинированный вариант следует рассмотреть, если мониторинг покажет, что частые кеш-промахи первой страницы заметно увеличивают время её загрузки.

Сравнение вариантов приведено в таблице:

| Критерий | **Cache-Aside** | Cache-Aside и Refresh-Ahead |
| --- | --- | --- |
| Описание | Страницы кешируются после обращения | Первые страницы часто просматриваемых статусов обновляются заранее, остальные — после обращения |
| Плюсы | Простая реализация, фоновых запросов нет, при отказе Redis данные читаются из MES DB | Первые страницы остаются прогретыми после истечения TTL, операторы реже ждут запрос к MES DB |
| Минусы | Первый запрос после очистки кеша или истечения TTL выполняется через MES DB | Требуются фоновая задача, настройка списка обновляемых статусов и дополнительные запросы к MES DB |

### Инвалидация кеша

Для программной инвалидации используется приём версионирования пространства ключей — namespace versioning. Он реализуется с помощью versioned keys: номер текущего поколения включается в каждый ключ страницы. Изменение статуса заказа и увеличение поколений его предыдущего и нового статуса выполняются в одной транзакции MES DB. При создании заказа в той же транзакции увеличивается поколение его начального статуса. Следующее чтение формирует ключи с новым поколением, поэтому все ранее кешированные страницы затронутого статуса сразу перестают использоваться.

Первое чтение страницы после создания заказа или изменения его статуса приводит к cache miss. Кеш остаётся эффективным, пока между изменениями списка операторы успевают запросить одну и ту же страницу несколько раз. Если измерения не подтвердят это соотношение, кеширование страниц следует пересмотреть.

Если транзакция MES DB завершилась ошибкой, не изменяются ни статус заказа, ни поколения. MES API записывает `ERROR`, увеличивает счётчик `order_status_transaction_errors_total` и возвращает ошибку изменения статуса. Старые ключи не перебираются и не удаляются синхронно: они перестают использоваться и удаляются по TTL.

Операторы должны увидеть изменение списка при следующем запросе, поскольку от доступности нового заказа зависит, кто возьмёт его в работу. Поэтому TTL не используется как допустимый срок показа устаревших данных: актуальность обеспечивает смена поколения в той же транзакции, что и изменение заказа.

TTL 5 минут используется для удаления ключей предыдущих поколений и ограничения времени жизни редко запрашиваемых страниц. Это начальная гипотеза, которую следует проверить по hit rate, объёму Redis и нагрузке на MES DB. Корректировка TTL не должна менять требование показывать обновлённый список при следующем запросе.

Рост `redis_cache_errors_total` и `order_status_transaction_errors_total` контролируется правилами оповещения. По первому счётчику поддержка проверяет Redis и возросшую нагрузку на MES DB, по второму — причину отката транзакции.

Ниже приведена матрица стратегий инвалидации по характеристикам:

| | Программная инвалидация | Временная инвалидация | Удаление по ключу | Полная очистка кеша |
| --- | --- | --- | --- | --- |
| **Преимущества** | Инвалидирует все страницы статуса увеличением одного номера версии без перебора ключей | Автоматически удаляет устаревшие значения по TTL | Подходит для заранее известного ключа | Не требует определять связанные ключи |
| **Недостатки** | Требует дополнительного чтения поколения из MES DB, старые ключи остаются до истечения TTL | До истечения TTL оператор может увидеть старый статус | Нельзя перечислить все существующие сочетания `page` и `size` без отдельного реестра | Удаляет страницы остальных статусов и увеличивает нагрузку на MES DB |
| **Применение** | Основная стратегия | Удаление ключей предыдущих поколений через 5 минут | Не используется | Не используется |
