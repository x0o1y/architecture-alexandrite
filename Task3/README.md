## Анализ

**Системы и порядок внедрения**

Сбор трассировок следует подключить в трёх приложениях:

1. CRM API — создаёт и изменяет заказ со стороны продавцов, работает с Shop DB и обменивается событиями с MES через RabbitMQ;
2. MES API — принимает партнёрские запросы, рассчитывает стоимость, изменяет производственные статусы, работает с MES DB, S3 и RabbitMQ;
3. Shop API — принимает заказ онлайн-магазина, сохраняет сведения о заказе в Shop DB и файл 3D-модели в S3.

Вызовы Shop DB, MES DB, S3 и RabbitMQ отражаются дочерними span, которые создаёт вызывающий API. В сообщения RabbitMQ добавляется контекст трассировки, чтобы обработка сообщения продолжала исходный trace.

Подключение выполняется поэтапно в порядке приоритета:

1. MES API, CRM API и обмен между ними через RabbitMQ — здесь создаются партнёрские заказы, рассчитывается стоимость и передаются статусы;
2. Shop API и его обращения к Shop DB и S3 — этот этап дополняет трассировкой путь заказов из онлайн-магазина.

**Места возможного сбоя или задержки**

- Shop API не сохранил заказ в Shop DB;
- Shop API или MES API не сохранил либо не получил файл 3D-модели из S3;
- MES API не завершил расчёт стоимости;
- CRM API или MES API не отправил событие в RabbitMQ;
- Сообщение RabbitMQ не было получено или обработано;
- CRM API или MES API не сохранил новый статус заказа;
- Запрос дашборда MES к MES DB выполнялся слишком долго;
- Партнёрский запрос завершился ошибкой или тайм-аутом.

**Данные трассировки**

Каждый trace должен содержать:

- Идентификаторы `trace_id`, `span_id` и родительского span;
- Название сервиса, экземпляра и окружения;
- Время начала и продолжительность операции;
- Название операции и результат её выполнения;
- Тип протокола и направление вызова;
- Шаблон HTTP-маршрута, метод и код ответа;
- Название очереди и тип операции RabbitMQ: публикация или обработка сообщения;
- Тип обращения к хранилищу: чтение или запись;
- Идентификатор заказа `order_id`, источник заказа и текущий статус;
- Номер попытки для операций, допускающих повторное выполнение;
- Код или класс ошибки, позволяющий определить вид сбоя; подробности и stack trace сохраняются в логах без чувствительных данных.

## Мотивация

Сейчас команда не видит полный путь заказа между Shop API, CRM API, RabbitMQ и MES API. Для поиска причины задержки приходится отдельно проверять системы и сопоставлять данные вручную. Трейсинг объединит операции одного заказа по `trace_id` и `order_id` и покажет продолжительность и результат каждого шага.

Трейсинг позволит:

- Найти компонент и операцию, на которых остановился заказ;
- Отличить медленный расчёт стоимости от задержки RabbitMQ или базы данных;
- Сопоставить партнёрский запрос с созданием заказа в CRM;
- Быстрее расследовать жалобы клиентов и проверять результат исправлений.

Внедрение трейсинга должно повлиять на следующие технические и бизнес-метрики:

| Тип | Метрика | Ожидаемое изменение |
| --- | --- | --- |
| Техническая | Среднее время расследования сбоя заказа | Сокращение |
| Техническая | Количество заказов, которые вовремя не перешли в следующий статус | Снижение |
| Техническая | p95 времени передачи заказа из CRM в MES | Снижение |
| Бизнес | Доля заказов, выполненных в согласованный срок | Увеличение |
| Бизнес | Количество обращений клиентов о неизвестном статусе заказа | Снижение |

## Предлагаемое решение

**Компоненты**

1. В Shop API и CRM API на Spring Boot подключить OpenTelemetry SDK для Java;
2. В MES API на C# подключить OpenTelemetry SDK для .NET;
3. Автоматически создавать span для входящих HTTP-запросов и обращений к PostgreSQL, S3 и RabbitMQ;
4. Добавить бизнес-span для создания заказа, расчёта стоимости и изменения статуса;
5. Развернуть OpenTelemetry Collector для приёма trace по OTLP, пакетной обработки и отправки в Jaeger;
6. Развернуть Jaeger для поиска и просмотра trace;
7. Использовать Elasticsearch как backend Jaeger и хранить trace в отдельных индексах 30 дней. Этот срок покрывает обещанный трёхнедельный цикл выполнения заказа и оставляет время на расследование задержек.

**Передача контекста**

Для HTTP используется заголовок W3C Trace Context. При публикации сообщения CRM API или MES API записывает контекст трассировки в заголовки RabbitMQ. Получатель извлекает контекст и создаёт дочерний span обработки сообщения.

`order_id` добавляется как атрибут span и позволяет найти операции заказа, которые не удалось связать одним trace. Это требуется для действий, разделённых длительным ожиданием или чтением состояния из базы данных.

Приложения отправляют данные трассировки в фоновом режиме. Недоступность OpenTelemetry Collector или Jaeger не должна останавливать создание и обработку заказов.

При расследовании сбоя сотрудник поддержки находит заказ в Jaeger по `order_id` или `trace_id` и проверяет последовательность операций, их продолжительность и ошибки.

### Мониторинг прохождения заказа

Раздел относится к дополнительной части задания. OpenTelemetry Collector преобразует завершённые span в метрики количества вызовов, ошибок и продолжительности операций. Метрики группируются по сервису и операции. `order_id` и `message_id` в ярлыки Prometheus не добавляются.

Prometheus сохраняет метрики, а Grafana отправляет уведомление при росте ошибок или превышении допустимой продолжительности создания заказа, расчёта стоимости и перехода статуса. Так автоматически контролируются технические этапы прохождения заказа, отражённые в trace.

Накопление сообщений контролируется собственными метриками RabbitMQ, а зависшие заказы — метриками количества и возраста заказов в статусе из решения по мониторингу. После срабатывания предупреждения сотрудник поддержки находит `order_id` через дашборд или логи, открывает соответствующий trace в Jaeger и проверяет причину задержки.

### Компромиссы

- Путь одного заказа может быть разделён между несколькими trace. Поэтому во все связанные с заказом span добавляется `order_id`, по которому поддержка находит его полную историю в Jaeger;
- Для операций, которые OpenTelemetry не может определить автоматически, потребуется доработка исходного кода и последующая поддержка трассировки в приложениях;
- Данные трассировки отправляются в фоновом режиме и не задерживают обработку заказов. При аварийном завершении приложения часть неотправленных span может быть потеряна. Этот риск принимается, чтобы сбой системы трейсинга не влиял на бизнес-операции.

### Безопасность

- Данные трассировки классифицируются по правилам компании. Для каждой категории применяются установленные требования к доступу, передаче, хранению и удалению данных;
- Jaeger UI и OpenTelemetry Collector доступны только из внутренней сети компании;
- Единственной точкой пользовательского доступа к Jaeger UI является аутентифицирующий reverse proxy, подключённый к корпоративному провайдеру идентификации по OpenID Connect;
- Reverse proxy предоставляет доступ на просмотр trace только сотрудникам поддержки, разработчикам и инженерам эксплуатации, входящим в разрешённую группу `tracing-viewers`;
- Администрирование Jaeger не выполняется через пользовательский UI и предоставляется инженерам эксплуатации отдельно на уровне инфраструктуры;
- Передача trace между приложениями, OpenTelemetry Collector и Jaeger защищается TLS;
- Reverse proxy журналирует обращения к Jaeger UI с идентификатором пользователя.
